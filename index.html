Sealgraf

Spend authorization for AI agents

The problem: an agent holding connected payment tools can spend first and explain later. No pre-spend check runs against limits the owner set, any approval happens on a surface the agent itself controls, and afterwards nothing proves what was approved, by whom, and why.

Sealgraf is the authorization layer: the agent checks owner-set limits before spending, obtains the owner's approval on a surface the agent cannot fake, and seals a verifiable receipt for every transaction.

My focus here: authorization design, approval enforcement, and failure handling. Sealgraf — case study

Problem — an agent holding connected payment tools can spend first and explain later: no pre-spend check runs against limits the owner set, any approval happens on a surface the agent controls, and afterwards nothing proves what was approved, by whom, and why.

My role — I designed and built the authorization layer and the integration packages for six agent frameworks.

Hardest decision — Approval has to happen on a surface the agent cannot fake: the owner approves out-of-band, and the agent only ever learns the outcome.

Architecture — five pieces, one direction of trust: the agent proposes, Sealgraf checks, the owner decides on their own surface, execution happens on any payment rail, and the receipt store seals the evidence.

Walkthrough — the owner sets a mandate in advance: scope, a per-purchase cap, a period cap, and an ask line above which a human must approve. An agent proposes a purchase; Sealgraf canonicalizes the action and hashes it (SHA-256) — the decision, approval, token, and receipt all cite that action hash. A deterministic decide step fires rules in a fixed order: agent identity, mandate active and inside its validity window, scope and per-purchase cap, then period cap. Under the ask line, the decision allows and a token is minted — and the decision itself is sealed to the ledger before any token exists. Over the ask line, the owner gets a doorbell (email or push carrying the facts and a link, never controls) and approves on their own authenticated surface; the approval is sealed, then the token is minted. The agent claims the token — claiming is not consumption — pays on any rail, and reports completion. At completion the engine re-validates the token, its expiry, and the mandate's current status and scope, then seals the receipt: one bundle holding the cited mandate version's terms, the action and its hash, the decision, the approval statement when one was needed, and the completion block.

When things change — the approval token is bound to the hash of the exact action approved, so changing any term of the purchase changes the action hash, and the minted token does not cover the new action. The token is single-use and valid for 15 minutes (900 seconds), and it is stored only as a hash. A pause, revoke, or tightening of the mandate that lands between approval and spending stops the spend, because completion re-checks the mandate as it stands now. A second receipt for one preauthorization cannot be created — a storage-level uniqueness constraint forbids it — and a purchase the owner already denied is denied again on an identical re-check.

What I built in the integrations — I personally designed and implemented the six framework packages — Dify (77 tests), CrewAI (64), LangChain (55), Vercel AI SDK (49), n8n (34), and Composio (23) — each live-tested end-to-end against the production service, with the approval loop verified on the server side, not just in the client.

Paper — the design is written up in “Approval You Can Verify: Owner-Approved Agent Spending with Sealed Evidence” (v1.1) — full text and PDF at sealgraf.com/paper.

Result — live product at sealgraf.com. The behaviors the suites and live loops validate: a changed action is not covered by an earlier approval, expired or already-used tokens fail at completion, and no second receipt can be sealed for one authorization.

Reify — case study

Problem — agent memory systems hand the model top-k clues and make it re-synthesize on every query. Most store only current state; even systems that keep validity windows don't surface the change itself as a queryable artifact — so "what changed?" has no direct answer.

My role — I built a local-first memory engine: a bitemporal graph where transitions are first-class data, hybrid retrieval, and MCP / REST / CLI surfaces.

Hardest decision — Make the memory layer itself the reasoner — reconsolidation on write and materialized inferences — instead of retrieval-time-only synthesis; and forget-by-default TTLs, so memory can explain and expire itself.

Why SQLite — plain SQL is truth: the whole store is one local SQLite file that any user can open and read directly (sqlite3 ~/.reify/store.db), with sqlite-vec holding embeddings in the same file. No server to run; a Postgres adapter is a v1 roadmap item, not a hidden dependency.

Why a bitemporal graph — facts carry bitemporal validity, and every change is stored as a Transition event: the change itself is data, not just the before and after states. New facts supersede old ones without erasing them — which is what makes "what changed?" a first-class query instead of another synthesis job handed to the model.

Retrieval — a hybrid pipeline: semantic, BM25, graph, temporal, and causal signals run in parallel, RRF-fused and cross-encoder reranked, token-budget-aware. Recall is metadata-first — tag → time → entity → BM25 → embeddings — and must work with embeddings disabled entirely.

The wedge example — Day 1: "I just got promoted from Senior to Staff Engineer." Day 30: "What's my title?" → "Staff Engineer." And: "Did anything change recently?" → "Yes — you were promoted from Senior to Staff Engineer 30 days ago." The second answer is the point: it reads the stored Transition; it isn't reconstructed.

Reproducible evaluation — make demo is the v0.1 acceptance bar: the first three steps of the wedge run end-to-end on a real MCP host with no LLM key, against a temp SQLite store with the deterministic extractor only — no API keys, no network. The repo's own stated limits: hosts other than the smoke-tested one are expected to work but have not been individually verified, and the project is pre-alpha and single-maintainer. An open evaluation harness also runs in CI against public memory benchmarks (LongMemEval, LoCoMo, BEAM); its numbers, and the matching caveats the repo attaches to them, are published in the README's Status section rather than quoted here.

git clone https://github.com/saiarung27/reify.git
cd reify
make install   # creates .venv, installs reify + dev extras
make demo      # runs the wedge end-to-end, no LLM key

Roadmap, not shipped — the Day-60 step, derived claims materialized across sessions ("What do I usually emphasize in promotion writeups?"), is a v0.4 item that requires the LLM-backed reconsolidator and sleep phase. The repo labels it roadmap; it is not claimed as working here.

Result — open source, at github.com/saiarung27/reify. make demo reproduces the wedge — the title change recalled across sessions, with the change itself directly answerable — and 442 tests cover the transition graph, the retrieval pipeline, and the MCP / REST / proxy surfaces.

My role — I built the verification pipeline (ownership cross-checks, photo provenance, price-vs-market), the fee ledger with its hard budget gate, and correction tracking.
